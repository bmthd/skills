# 委任

時間のかかる仕事や範囲の広い仕事は裏で進め、ペアプロのループを待たせない。委任先への指示には、いつも次の三つを入れる。**隔離された作業場所**（最新の既定ブランチから作った専用の git worktree。ユーザーのチェックアウトと開発サーバーには触らない）、**止まる条件**（作業せずに報告して止まるとき）、**報告の形**（何を返すか。ユーザーの言語で）。

報告は数行で伝え、判断が要る点は `AskUserQuestion` の選択肢にする。文脈を持っている委任先（原因を突き止めた委任先、マージのキューを回している委任先）は、作り直さずに `SendMessage` で続けさせる。

## PR を監視してマージする

バックグラウンドのサブエージェントが次を行う。

1. チェックが終わるのを待つ（`gh pr checks <n> --watch`）。
2. Preview のジョブの後、レビュー観点のリンクがすべて 200 を返すことを確かめる（転送はたどる）。
3. ブランチを消さずにスカッシュでマージする。ユーザーのチェックアウトがそのブランチを使っていることがあるため。

チェックの失敗が、その PR 自身の単純な誤りだとはっきりしないとき、またはマージにブランチ保護の迂回が要るときは、止まって報告させる（`--admin` を使うかはユーザーが決め、委任先は決めない）。

複数の PR は**マージのキュー**にする。順番は最初に伝え、新しい PR は動いている委任先のキューの最後に足す。二つの PR の CI がお互いの直しを必要としていると、キューは止まる。片方のコミットをもう片方に移してそちらをマージし、差分の無くなった PR はコメントを付けてクローズする。

## 失敗を調査する

バックグラウンドのサブエージェントが失敗を再現し、根本原因を根拠（`file:line`）付きで突き止め、既定ブランチでも落ちるかを確かめる。直すのは、原因のはっきりした小さな失敗だけにする（たとえば、今日の日付に左右されるテストに固定の時計を渡す）。その直しは別の PR にする。直しに仕様の判断が要るとき、原因が別の開いている PR にあるとき、直しが多くのファイルに広がるときは、選択肢とおすすめを添えて報告して止まる。ユーザーが選んだら、同じ委任先に返す。

## コードベースに横展開する

機械的な一括変更は、Orca の専用の worktree でコーディングエージェントに任せる。

```text
orca worktree create --repo id:<repoId> --name <task> --no-parent --agent codex --prompt "<brief>" --json
```

指示には次を書く。

- 置き換える書き方
- 対象と対象外
- 触らないテスト
- 無視してよい既知の失敗
- 「まず計画を見せて。承認したら PR を出すところまで進めて。マージはしない」

そのあと、次の順で進める。

1. `orca terminal wait --terminal <handle> --for tui-idle --timeout-ms <ms>` で計画が出るのを待ち、`orca terminal read` で読む。
2. 計画を指示と突き合わせ、`orca terminal send --text "<承認>" --enter` で承認するか、直させる。
3. worktree のコメントを設定し、Orca のカードで状態が見えるようにしてから、あとは任せる。

横展開の PR も、ほかの PR と同じようにマージのキューに入れる。
