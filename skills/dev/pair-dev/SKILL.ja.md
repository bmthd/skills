# Pair Dev

ユーザーは動いているアプリを見て指摘し、あなたは手を動かす。指摘は Issue か、専用のブランチでの直しか、委任する仕事のどれかになる。時間のかかる部分は委任先に任せ、会話は次の指摘へ進む。足りないのはユーザーの注意なので、一回の返事は短くし、待てることはユーザーの目の前に置かない。

## 1. セッションを始める

1. リポジトリの規則（`AGENTS.md`、`CLAUDE.md`）を読み、scripts から開発サーバーのコマンドを探す。
2. いま待ち受けているポートを一覧する（`lsof -iTCP -sTCP:LISTEN -P`）。ほかの worktree が開発サーバーを動かしていることが多い。空いているポートを選び、そのポートに固定してバックグラウンドで起動する（Vite なら `--port <n> --strictPort`）。
3. URL が 200 を返すまで待ち、`orca tab create --url <url> --json` で開く（ブラウザのコマンドは `orca-cli` スキルを読み込んで使う）。返ってきた `browserPageId` を**自分のタブ**として控える。
4. スクリーンショットを 1 枚撮って表示を確かめ、URL、ポートとそれを選んだ理由、いまのブランチを伝える。そのうえで、気になるところを尋ねる。

**ユーザーのタブはユーザーのもの。** ユーザーは自分のタブを見ていて、あなたのタブを閉じることもある。ユーザーのタブは、同じものを見るために読むだけにする（`tab list` で表示中のページを探し、スクリーンショットを撮る）。クリック、操作、幅の変更は自分のタブでだけ行い、自分のタブが無くなっていたら一時的なタブを開く。一時的なタブは終わったら閉じる。

## 2. 指摘を一つずつ扱う

まず指摘を分類する。分類で、その後の手順がすべて決まる。

| 指摘 | 手順 |
|---|---|
| 「Issue にして」 | **Issue**: 原因のコードを探し、いまの動き（`file:line` 付き）と直したあとの動きを書いて `gh issue create` する。推測で書いた部分は、返事でそうと伝える。 |
| 見た目や動きの直し | **直す**（下）。 |
| 「PR して」 | **出す**（下）。 |
| 同じ書き方がコードベースのあちこちにある | 目の前のファイルだけ直し、残りは**横展開**として提案する（[delegation.ja.md](delegation.ja.md)）。 |
| CI の監視、マージ、失敗の調査 | 委任する（[delegation.ja.md](delegation.ja.md)）。 |

### 直す

1. 最新の既定ブランチから、話題ごとにブランチを切る: `git fetch && git switch -c <topic> origin/<default>`。マージ前の別の話題の上に、新しい話題を重ねない。
2. 直す前に原因を見つける。レイアウトの不具合は、問題の操作の前と後で自分のタブを測る（`orca eval` で `getBoundingClientRect` や `getComputedStyle` を読む）。数値が原因を示す。
3. ユーザーが決めるべき設計の選択（警告の見た目、ダイアログに置くボタン）があれば、`AskUserQuestion` で一度だけ尋ねる。プレビューを付け、おすすめを先頭に置く。それ以外は自分で決める。
4. UI ライブラリの部品で組む。素の要素を組み立てる前に、ライブラリの export を探す（`Box` に `display="flex"` は `Flex`、手組みの `<table>` はライブラリの表）。候補が二つあれば、それぞれのコストを比べ（両方ビルドしてチャンクの大きさを比べる）、役目を果たす軽い方を選ぶ。
5. テストは**振る舞い**だけを書く。何が保存されるか、どこへ移るか、何が作られるか。先に書いて、失敗するのを見る。見た目（色、余白、ボタンの順番、どのボタンがあるか）とライブラリ自身の機能（Esc でダイアログが閉じる）は、ユーザーが目で確かめるものなので、テストに入れない。
6. 見た目を変えてはいけないリファクタリングでは、対象の要素の計算済みスタイルを変更前に記録し、変更後と比べる。「同一」か、違いそのものを伝える。
7. リポジトリの lint、format、型チェック、テストのコマンドを流す。テストが落ちたら、既定ブランチでも落ちるかを確かめてから、自分のせいかどうかを言う。
8. 数行で伝える。何を変えたか（`file:line`）、何を確かめたか、何を確かめていないか、ブランチとコミット前の状態。最後に次の指摘を尋ねる。

### 出す

リポジトリのメッセージの書き方でコミットし、push し、テンプレートに沿って PR を出す。レビュー観点には、変えたページへのリンクを添える。PR は委任先に監視とマージを任せ、次の指摘へ戻る。同じファイルを触る別の PR が開いていれば、どちらかが衝突することを伝える。

## 3. ループを安全に保つ

- **ペアプロ中の stash は罠になる。** 二つのビルドを比べるために作業を stash すると、変更が stash に残ったままになりやすい。代わりにファイルを脇へコピーし、差し替えて測り、コピーを戻し、`git diff --stat` で変更が残っていることを確かめる。
- **開発サーバーは再起動する。** ブランチを切り替えたり設定の変更を取り込んだりすると再起動するので、落ちたと言う前に 200 が返るまで待つ。
- **Orca のランタイムはときどき接続を落とす**（`runtime_unavailable`）。同じコマンドを一、二度やり直す。`browser_tab_not_found` なら、ID を使い回さずにタブを一覧し直す。
- ユーザーがやり方について直したこと（何をテストするか、どの部品を使うか、どこに置くか）は、長く効く好みとしてメモリに残し、次のセッションをそこから始める。
