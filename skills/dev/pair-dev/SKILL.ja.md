# Pair Dev

ユーザーは動いているアプリを見て指摘し、あなたは手を動かす。指摘は Issue か、専用のブランチでの直しか、委任する仕事のどれかになる。時間のかかる部分は委任先に任せ、会話は次の指摘へ進む。足りないのはユーザーの注意なので、一回の返事は短くし、待てることはユーザーの目の前に置かない。

**共有の画面**とは、動いているアプリが二人とも見える場所のこと。ブラウザのタブ、シミュレーターやエミュレーター、デスクトップのウィンドウなどで、ターミナルマルチプレクサのペインで開くか、自動操作のツールで動かす。

## 1. セッションを始める

1. リポジトリのエージェント向けの規則（`AGENTS.md` かそれに当たるファイル）を読み、開発中のアプリの起動方法を探す。
2. ほかの worktree がすでに使っているもの（ポート、シミュレーターのデバイス、エミュレーター）を確かめる。空いているものを選び、それに固定してバックグラウンドで起動する。固定しないと、知らないうちに別のものへずれる。
3. アプリの準備ができるまで待ち、共有の画面で開く。開いたものの ID を**自分の画面**として控える。
4. スクリーンショットを 1 枚撮って表示を確かめ、アプリが動いている場所、選んだものとその理由、いまのブランチを伝える。そのうえで、気になるところを尋ねる。

**ユーザーの画面はユーザーのもの。** ユーザーは自分の画面を見ていて、あなたの画面を閉じることもある。ユーザーの画面は、同じものを見るために読むだけにする。操作、大きさの変更、画面の移動は自分の画面でだけ行い、自分の画面が無くなっていたら一時的な画面を開く。一時的な画面は終わったら閉じる。

## 2. 指摘を一つずつ扱う

まず指摘を分類する。分類で、その後の手順がすべて決まる。

| 指摘 | 手順 |
|---|---|
| 「Issue にして」 | **Issue**: 原因のコードを探し、いまの動き（`file:line` 付き）と直したあとの動きを書いて Issue にする。推測で書いた部分は、返事でそうと伝える。 |
| 見た目や動きの直し | **直す**（下）。 |
| 「PR して」 | **出す**（下）。 |
| 同じ書き方がコードベースのあちこちにある | 目の前のファイルだけ直し、残りは**横展開**として提案する（[delegation.ja.md](delegation.ja.md)）。 |
| CI の監視、マージ、失敗の調査 | 委任する（[delegation.ja.md](delegation.ja.md)）。 |

### 直す

1. 最新の既定ブランチから、話題ごとにブランチを切る: `git fetch && git switch -c <topic> origin/<default>`。マージ前の別の話題の上に、新しい話題を重ねない。
2. 直す前に原因を見つける。レイアウトの不具合は、問題の操作の前と後で自分の画面を測る（要素の位置と大きさ、計算済みのスタイルを、自動操作のツールかプラットフォームのインスペクターで読む）。数値が原因を示す。
3. ユーザーが決めるべき設計の選択（警告の見た目、ダイアログで選べる操作）があれば、選択式の質問で一度だけ尋ねる（ハーネスに構造化された質問のツールがあればそれを使う）。プレビューを付け、おすすめを先頭に置く。それ以外は自分で決める。
4. プロジェクトの UI キットで組む。部品を自分で組み立てる前に、キットが何を export しているかを探す。候補が二つあれば、それぞれのコスト（ビルドに足される大きさと依存）を比べ、役目を果たす軽い方を選ぶ。
5. テストは**振る舞い**だけを書く。何が保存されるか、どこへ移るか、何が作られるか。先に書いて、失敗するのを見る。見た目（色、余白、順番、どの操作があるか）と UI キット自身の機能は、ユーザーが目で確かめるものなので、テストに入れない。
6. 見た目を変えてはいけないリファクタリングでは、対象の要素の位置、大きさ、スタイルを変更前に測って記録し、変更後と比べる。「同一」か、違いそのものを伝える。
7. リポジトリの lint、format、型チェック、テストのコマンドを流す。テストが落ちたら、既定ブランチでも落ちるかを確かめてから、自分のせいかどうかを言う。
8. 数行で伝える。何を変えたか（`file:line`）、何を確かめたか、何を確かめていないか、ブランチとコミット前の状態。最後に次の指摘を尋ねる。

### 出す

リポジトリのメッセージの書き方でコミットし、push し、テンプレートに沿って PR を出す。レビューする人が変更をアプリのどこで見られるかを書く。PR は委任先に監視とマージを任せ、次の指摘へ戻る。同じファイルを触る別の PR が開いていれば、どちらかが衝突することを伝える。

## 3. ループを安全に保つ

- **ペアプロ中の stash は罠になる。** 二つのビルドを比べるために作業を stash すると、変更が stash に残ったままになりやすい。代わりにファイルを脇へコピーし、差し替えて測り、コピーを戻し、`git diff --stat` で変更が残っていることを確かめる。
- **動いているアプリは再起動する。** ブランチを切り替えたり設定の変更を取り込んだりすると再起動するので、落ちたと言う前に準備ができるまで待つ。
- **共有の画面との接続はときどき落ちる。** 同じコマンドを一、二度やり直す。画面が見つからないと言われたら、古い ID を使い回さずに開いているものを一覧し直す。
- ユーザーがやり方について直したこと（何をテストするか、どの部品を使うか、どこに置くか）は、長く効く好みとしてメモリに残し、次のセッションをそこから始める。
