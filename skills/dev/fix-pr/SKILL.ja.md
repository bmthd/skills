# Fix PR

レビュー指摘を推測で処理せずに、GitHub のプルリクエストをマージ可能な状態へ持っていく。

## 手順

### 1. PR を特定する

`args` を読む。

- `args` に PR 番号があればそれを使う。
- なければ、現在の会話で対象の PR が明確に示されていればそれを使う。
- それもなければ、現在のリポジトリで `gh pr view --json number,url,headRefName,baseRefName` を実行し、現在のブランチの PR を特定する。
- PR を特定できない場合は、ユーザーに PR 番号を尋ねて停止する。

`args` に `--auto` が含まれる場合のみ `auto=true` とする。

### 2. 編集前に状態を確認する

現在の状態を集める:

```bash
gh pr view <PR> --json number,title,url,state,isDraft,mergeStateStatus,reviewDecision,headRefName,baseRefName,comments,reviews,reviewThreads,statusCheckRollup
gh pr checks <PR>
git status --short
```

失敗した実行がある場合は、`gh run view --log-failed` で失敗チェックのログも確認する。

無関係な未コミット変更には手を出さない。ローカルの変更が必要な修正と直接衝突する場合は、進め方をユーザーに尋ねる。

編集の前に、作業ツリーが PR の head ブランチ上にあることを確認する:

- 既に `headRefName` にいるなら続行する。
- `headRefName` にいなくて無関係なローカル変更がある場合は、ブランチを切り替える前に確認する。
- それ以外は、`gh pr checkout <PR>` などリポジトリの通常のワークフローで PR ブランチをチェックアウトする。
- PR の `headRefName` 以外のブランチへは、決してコミットもプッシュもしない。

### 3. レビューコメントの扱い

レビューコメントは自動的に正しいわけではない。

対応が必要なレビューコメントがあり、`--auto` が渡されていない場合は、表を出力してユーザーの確認を待ってからコードを編集する:

| コメント | 対応案 | 理由 | リスク |
|---|---|---|---|
| `<file:line の要約>` | 受け入れ / 却下 / 調査 | `<なぜ>` | 低 / 中 / 高 |

`--auto` が渡された場合は、コメントを自律的に処理する:

- 明らかに正しい変更要求は適用する。
- 曖昧な提案は編集前に調査する。
- 技術的に誤った提案は適用せず、最終報告でその理由を説明する。
- 大規模なリファクタより最小限の修正を優先する。

### 4. マージ可能にする

ブロッカーは次の順に片付ける:

1. 変更要求と未解決のレビュースレッド。
2. 失敗している必須チェック。
3. ベースブランチに対して遅れているブランチ。
4. マージコンフリクト。
5. ローカル検証の不足。

コードや挙動の修正では、可能な限りテスト駆動開発に従う: まず失敗を再現し、最小の修正を当て、通ることを検証する。

通常の非対話コマンドを使う。ベースからブランチを更新する必要がある場合は、まず PR の head ブランチにいることを確認する。リポジトリで定められたマージ/リベースの慣習を優先する。慣習がなければ、履歴を書き換えないベースブランチからのマージを優先する。ユーザーの明示的な承認なしに、公開済みの PR 履歴をリベース・強制プッシュ・その他の方法で書き換えない。

### 5. 検証してプッシュする

修正範囲をカバーする対象を絞ったテストやチェックを実行する。リポジトリに明らかな全体検証コマンドがあり、実行が妥当ならそれも実行する。

プッシュ前に確認する:

```bash
git status --short
git diff
```

PR ブランチへ送るべき意図的なローカル変更がある場合にのみコミットしてプッシュする。コミットのスタイルはリポジトリのものに合わせる。変更が不要ならコミットとプッシュを飛ばし、現在の PR の状態を報告する。

### 6. PR の状態を再確認する

プッシュ後に再実行する:

```bash
gh pr checks <PR>
gh pr view <PR> --json mergeStateStatus,reviewDecision,statusCheckRollup
```

チェックがまだ pending なら、CI 待ちであることを報告する。チェックが失敗している場合は、権限・シークレット不足・不安定な外部サービス・ユーザーの方針で止められない限り調査を続ける。

修正後も `reviewDecision` が `CHANGES_REQUESTED` のままだったり必須スレッドが未解決なら、その PR をマージ可能と呼ばない。レビュアーの対応がまだ必要であることを報告する。リポジトリのワークフロー上妥当であれば、却下したレビュー提案とその技術的理由を簡潔な PR コメントとして残す。

## 出力

完了したら次を報告する:

- PR の URL。
- 行った修正。
- 実行した検証とその結果。
- 残っているブロッカー (あれば)。
- 意図的に却下したレビュー提案と、その理由。

## よくある失敗

- `--auto` が渡されていないのに、レビューコメントの表を提示する前に編集を始めない。
- レビュー提案が正しいと決めつけない。
- ユーザーが明示的に承認するか、リポジトリの指示が要求しない限り、強制プッシュ・リベース・PR 履歴の書き換えをしない。
- `gh pr view` と `gh pr checks` で確認できるまでマージ可能と主張しない。確認できないなら、何が未確定かを明示する。
