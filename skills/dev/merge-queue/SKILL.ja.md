# Merge Queue

複数のプルリクエストを受け取ってキューに並べ、GitHub の Merge Queue と同じやり方で
1 つずつマージ済みまで進める — 逐次的に、常に最新のベースに対して。マージを妨げるものは
**一度に 1 つずつ、自律的に** 解消する: 承認する、ブランチを更新する、単純なコンフリクトを解消する、
単純な CI 失敗を直す。呼び出した人はこれを任せて立ち去る。安全にできることをすべて終わらせ、
本当に人間が必要なものだけを整理して報告するのが仕事。

## 約束事 (何かをする前に読む)

- **先にゲート、次に作業。** どの PR にも手を付ける前に全 PR を評価する。**1 つも**
  「今マージできる」でも「自動解消できる」でもないなら、停止してユーザーに尋ねる — 中途半端に始めない。
- **昼休みで止めない。** 対応可能な PR が 1 つでもあれば、確認を求めずに進める。人間の判断が必要と
  判明した PR は *最終報告に回す* のであって、実行全体を止める理由ではない。
- **自律には境界がある。** 解消するのは *機械的* なブロッカーのみ。プロダクト/ロジックの判断を要するもの
  — 意味的なマージコンフリクト、本物のテスト失敗、draft の ready 化 — は先送りし、決して当て推量しない。
- **ここでの操作はすべて外向きで取り消しにくい** (承認、push、マージ)。`args` の PR 番号は
  *その PR* をマージする権限であって、それ以外の権限ではない。
- **応答性を保つ。** 時間のかかる部分 (CI 実行、ブランチの再計算) はバックグラウンドタスクで走らせ、
  セッションは常に新しい PR をキューに受け入れたり、他の PR を進めたりできる状態にしておく。
  1 つの PR で待ちに入って固まらない。

## キューボード (毎ターン描画する)

ボードが唯一の真実であり、ユーザーが進捗を見る唯一の窓。コンテキスト圧縮を越えて残るよう
状態ファイルに保持し、**何かが変わったターンでは必ず返答内に再描画する**:

```bash
board="$(git rev-parse --show-toplevel)/.git/merge-queue-board.md"   # .git 内 → 決してコミットされない
```

ボードは常に、ユーザーが追う列をちょうど備えた表 + 進捗行:

```
### Merge Queue — 2/5 完了 (40%) · 進行中 1 · 先送り 1

| # | PR   | ブランチ        | 概要                       | 判定               |
|---|------|-----------------|----------------------------|--------------------|
| 1 | #12  | feat/login      | OAuth ログインを追加       | ✅ マージ済み      |
| 2 | #13  | fix/nav-crash   | null による nav クラッシュ修正 | ✅ マージ済み  |
| 3 | #14  | chore/bump-deps | 依存の更新                 | 🔧 ブランチ更新中 (bg) |
| 4 | #15  | feat/export-csv | CSV エクスポート           | ⏳ 待機中          |
| 5 | #16  | feat/redesign   | ダッシュボード刷新         | ⏭️ 先送り: 意味的コンフリクト |
```

- **判定** 列はマージ可能性の判断 + 現在の作業。語彙:
  `✅ マージ済み` · `🔵 今マージ可能` · `🔧 <作業> (bg)` (承認中 / ブランチ更新中 /
  コンフリクト解消中 / lint 修正中 / CI 再実行中) · `⏳ 待機中` · `⏭️ 先送り: <理由>`
  · `⛔ ブロック: <理由>` (ゲート不通過、ユーザー対応が必要)。
- **進捗行** = マージ済み ÷ 総数のパーセンテージ、加えて進行中と先送りの件数。PR の状態が変わるたびに更新する。
- ボードファイルを書き換えたうえで、現在の表を返答に貼る。これは飾りではない —
  ユーザーが昼休み明けに状況を確認する手段そのもの。

## 手順 (厳密に従うこと)

### 1. 入力の解釈と事前確認

`args` から PR 番号を読む (スペースまたはカンマ区切り)。空ならどの PR か尋ねる。次に:

```bash
gh auth status          # 認証済みであること
gh repo view --json nameWithOwner,defaultBranchRef -q '.nameWithOwner, .defaultBranchRef.name'
```

**このリポジトリのクリーンなチェックアウト** で作業する (未コミット変更なし — `git status` がクリーン)。
作業ツリーが汚れている場合は停止してユーザーに伝える。ユーザーの作業を stash してはならない。

### 2. 全 PR を評価する (ゲート)

各 PR について、状態を一括で取得する:

```bash
gh pr view <n> --json number,title,isDraft,mergeable,mergeStateStatus,reviewDecision,\
headRefName,baseRefName,statusCheckRollup,author,url
```

`mergeStateStatus` とレビュー状態を分類に対応させる:

| 状態 | 意味 | 分類 |
|---|---|---|
| `CLEAN` | 最新、承認済み、チェック緑 | **今マージ** |
| `BEHIND` | ベースに対してブランチが遅れている | **自動解消** → ブランチ更新 |
| `BLOCKED` (承認だけが不足) | レビューが必要 | **自動解消** → 承認 |
| `UNSTABLE` / チェック失敗 | チェックが赤 | **調査** (§4.3) — 単純な修正か先送り |
| `DIRTY` | マージコンフリクト | **調査** (§4.2) — 単純な解消か先送り |
| `DRAFT` / `isDraft` | draft PR | **先送り** — ready 化は人間が行う |
| `UNKNOWN` | GitHub が計算中 | 分類前に数回ポーリングし直す |

各 PR — 番号、ブランチ (`headRefName`)、1 行の概要 (タイトル)、判定 — を **キューボード** に
書き込み、描画する。これがユーザーが席を外す前に見る計画になる。

**ゲート判定:** すべての PR が **先送り** に落ちる場合 (今マージも自動解消も 1 つも無い) は停止する。
ボードは全行を理由付きの `⛔ ブロック` / `⏭️ 先送り` として示す。どう進めるかユーザーに尋ねる。
そうでなければ続行する。

### 3. キューの順序を決める

同じベースブランチを共有する PR は **逐次的に**、渡された順で処理する (ユーザーが依存関係を明示した
場合はそれに従う)。逐次であることこそが要点: 各 PR は直前の PR がマージされた *後に* 最新化されるため、
常に実際の合成結果をテストすることになる — merge queue がやっているのはまさにこれ。
ベースブランチが異なるものは独立したレーンとして扱う。

### 4. 各 PR をマージ済みまで進める (バックグラウンドで)

ここでの待ち — push 後の CI 再実行、`update-branch` の再計算 — は数分かかる。
**バックグラウンドタスクとして実行する** (`Bash` の `run_in_background: true`) ことで固まらない:
待ちを開始し、ボード上でその PR を `🔧 <作業> (bg)` にし、空いたセッションで次の独立した PR を進めたり、
ボードを更新したり、ユーザーから新しい PR を受け取ったりする。バックグラウンドコマンドが終わると
その結果とともに再度呼び出されるので、そのときボードに反映する。待つためにフォアグラウンドで `sleep`
しない。バックグラウンドのポーリングループが定石
(例: `until gh pr checks <n> | grep -qv pending; do sleep 20; done`)。

対象の PR については、ブロッカーを **一度に 1 つずつ** 解消し、修正のたびに状態を確認し直す
(修正はしばしば `mergeStateStatus` を変える)。遷移のたびにボードの判定を更新する。
CLEAN になるか先送りになるまで繰り返す。

#### 4.1 遅れている (`BEHIND`)
```bash
gh pr update-branch <n>          # サーバー側でベースを PR ブランチにマージする
```
その後、チェックの再実行を待つ (§4.4)。update-branch 自体がコンフリクトを報告したら §4.2 として扱う。

#### 4.2 コンフリクト (`DIRTY`)
現在のベースに対してローカルで解消する:
```bash
git fetch origin
git switch <headRefName> && git pull
git merge origin/<baseRefName>
```
- **単純** — ロックファイル/生成ファイルだけのコンフリクト (再生成する)、または重なりのない些細な hunk:
  解消してコミットし、`git push`。
- **意味的** — 実ソース/ロジックの重なる編集: **先送り**。`git merge --abort` して報告用に記録する。
  意図を当て推量しない。

#### 4.3 CI 失敗 (`UNSTABLE` / 赤いチェック)
```bash
gh pr checks <n>                 # どのチェックが失敗したか見る
```
対象は **単純で機械的な** 失敗のみ:
- フォーマット / lint の自動修正 (`mise run fmt`, `prettier -w`, `eslint --fix`, `cargo fmt`,
  `gofmt` — リポジトリが使っているもの)。コミットして push。
- 古い生成ファイル / ロックファイル → 再生成して push。
- 明らかに 1 件だけ不安定なチェック → **一度だけ** 再実行する (`gh run rerun --failed`)。

それ以外 — 本物のユニット/結合テスト失敗、コード修正を要する型エラー、セキュリティスキャン — は
**先送り**。ここでプロダクトロジックをデバッグするのは仕事ではない。

#### 4.4 承認不足 (レビュー待ちの `BLOCKED`)
```bash
gh pr review <n> --approve -b "Approved via merge-queue"
```
自分が PR の作者なら自己承認はできず、ブランチ保護が第三者を要求することもある。その場合は
**先送り** する (「他者の承認が必要」と記録する)。

#### 4.5 マージ
PR が CLEAN になったら、リポジトリの慣習でマージする (`git log` やリポジトリ設定を確認。既定は squash):
```bash
gh pr merge <n> --squash --delete-branch
git switch <baseRefName> && git pull --ff-only   # 次の PR のためにローカルのベースを更新
```

### 5. キューを進める (追加も受け付け続ける)

マージ後、**残りの** PR を §2 から再評価する — たった今のマージで、次の PR はたいてい `BEHIND` に、
ときに `DIRTY` になる。進捗行を更新し、キューが空になるまで続ける。

**新しい PR はいつでも歓迎。** 実行中にユーザーがさらに PR 番号を渡してきたら、新しい行として追加し、
評価し (§2)、キューに差し込む — 追加を受け付けるために現在の PR の完了を待たせない。
遅い作業をバックグラウンド化しているので、常にその余裕がある。

### 6. 報告

ボードそのものが進行中の報告 — ユーザーはいつでも読める。キューが空になったら (あるいは先送りだけで
完全に停止したら)、最終描画と具体的な内容を投稿する:
- ✅ マージ済み (PR 番号/リンク付き)
- 🔧 自動解消してマージしたもの、および *何をしたか* (承認 / 更新 / lint 修正 / …)
- ⏭️ 先送り — それぞれ具体的なブロッカーと、必要な人間の対応
- 再実行したもの、ユーザーのブランチへ push したもの

## 危険信号 — 押し通さず、停止するか先送りする

- **実ソースコードのコンフリクトを、どちらかを選んで解消しようとしている。** 先送り。
- **テストが失敗し、通すためにプロダクトコードを編集しようとしている。** 範囲外 — 先送り。
- **draft を「ready」にしたり、変更要求を却下したくなっている。** それは人間の判断 — 先送り。
- **`--force` / `--admin` / ブランチ保護の回避。** 決してしない。保護がマージを妨げているなら、
  それは意図的なゲート — 先送りする。
- **対応可能なものが無いのに編集を始めてしまった。** §2 のゲートは停止を意味する。

## 落とし穴

- **汚れた作業ツリー**: このスキルはコミットを push し、ブランチを切り替える。`git status` が
  クリーンでなければ実行を拒否する — ユーザーのローカル作業を stash したり壊したりしてはならない。
- **自己承認は不可能**: GitHub は自分の PR の承認を拒否する。単独リポジトリでは承認ブロッカーを
  自律的に解消できない。ループせずに表面化させる。
- **`mergeStateStatus` は遅れる**: push/更新の直後は GitHub が再計算する間 `UNKNOWN` になる。
  ブロックと判断する前に数回ポーリングする (短い sleep で)。
- **`UNSTABLE` でもマージできることがある**: これは *必須でない* チェックが赤いという意味。
  必須チェックが緑でポリシー上許されるなら、そのままマージできる場合がある — 実際にはゲートでない
  チェックを「直そう」としない。
- **並列ではなく逐次**: 同じベースの 2 つの PR を同時に更新/マージしない — 存在しない組み合わせを
  テストすることになる。1 つずつ、マージのたびにリベースし直す。
- **不安定なチェックの再実行は一度だけ**: 2 回失敗するチェックは不安定なのではない。先送りする。
- **バックグラウンド ≠ 同一ベースの同時マージ**: *待ち* をバックグラウンド化するのは良く、応答性を
  保てるが、マージは依然としてベースごとに 1 件ずつ。同じベースの 2 つの PR を並行して
  `gh pr merge` に到達させない — キューが存在しない組み合わせをテストすることになる。
- **ボードは圧縮を越えて残す**: ボードは自分の文脈だけでなく `.git/merge-queue-board.md` に置く。
  再開時はまずそのファイルを読み戻してから描画し、進捗を失わない。
