# Dispatch Issues

`gh` で着手可能な GitHub Issue を見つけ、何に取り組むかをユーザーに選ばせ、
その後は指揮官として独立した issue 作業をサブエージェントに並列で割り当てる。

## 必須サブスキル

- **必須:** issue の作業対象が決まったら `commander` を使う。
  指揮官は実装・テスト・コミット・push・issue の編集を自分では行わない。

## 手順

### 1. 依頼を解釈する

`args` を読む。空なら、どのリポジトリ・ラベル・キーワード・issue 種別を検索するか尋ねる。次を抽出する:

- リポジトリの範囲。曖昧さがない場合に限り、現在の GitHub リポジトリを既定にする。
- 検索フィルタ: ラベル、マイルストーン、担当者、状態、キーワード、件数上限。
- 選択モード: 既定はユーザー選択。自動選択は明示的に依頼された場合のみ。
- 割り当ての意図: トリアージのみ、実装、レビュー、ドキュメント、あるいはユーザーが指定した別の成果。

### 2. 事前確認

```bash
gh auth status
gh repo view --json nameWithOwner,defaultBranchRef -q '.nameWithOwner + " " + .defaultBranchRef.name'
```

認証に失敗したら停止し、ユーザーに認証を依頼する。探索中は読み取り専用の `gh issue` コマンドを使う。
ユーザーが明示的にその状態変更を依頼しない限り、issue・ラベル・担当・プロジェクト・コメントを編集しない
— 唯一の常設例外は、割り当てられたエージェントが自分の issue で行き詰まりを報告する場合 (手順 5)。

### 2b. ベースラインを検証する (省略しない)

issue はあるツリーを前提に書かれている。いま自分がいるチェックアウトがそのツリーとは限らない。
誤ったベースラインに並列エージェントを送り込むと全員分が無駄になるので、手順 5 の **前に** ベースラインを確定する。

```bash
git status -sb
git log --oneline -1
git fetch origin --quiet
git log --oneline -1 origin/main
git merge-base --is-ancestor HEAD origin/main && echo "on main" || echo "DIVERGED"
```

そのうえで **issue の本文をツリーと突き合わせて抜き取り検査する**。issue はファイルパスと行番号を挙げている。
2〜3 件を実際に解決する:

```bash
wc -l <issue が挙げるファイル>
grep -n '<issue に引用された正確な断片>' <file>
```

次のいずれかに当てはまる場合は停止してユーザーに尋ねる:

- **detached HEAD**、または HEAD が `origin/main` から分岐している。
- 挙げられたファイルが存在しない、または長さが issue の示唆と大きく異なる。
- 挙げられたシンボル/断片が存在しない (その機能が未マージのブランチにある)。
- issue の行番号が数行を超えてずれている。

単にずれているだけの行番号は問題ない — ただし **各サブエージェントに補正後の行を伝える**
(「issue は 583 と言っているが、このブランチでは 582」)。伝えないと誤った場所を編集する。

### 2c. 切り替える前に、参照されていないコミットを保全する

HEAD が detached で、どのブランチにも含まれないコミットがある場合、切り替えるとそれらは reflog 経由でしか
到達できなくなり、いずれ `gc` に回収される。作業ブランチを作る **前に** 名前を付ける:

```bash
git branch --contains <sha>          # 出力が空 = 何もそれを指していない
git branch wip/detached-<short-sha> <sha>
git checkout -b <work-branch> origin/main
```

救出ブランチをユーザーに報告する。決して `reset`・`rebase`・削除をしない。

### 3. 候補 issue を探索する

広く始めて、有望な issue を掘り下げる:

```bash
gh issue list --state open --limit 30
gh issue list --state open --search 'is:issue is:open no:assignee' --limit 30
gh issue list --state open --label 'help wanted' --limit 30
gh issue view <number> --comments --json number,title,body,labels,assignees,comments,url,state
```

フィルタはリポジトリの語彙 (`bug`, `enhancement`, `good first issue`, `priority`, `needs-triage`) に
合わせる。分類の前にコメントを確認する。ラベルだけでは足りない。

### 4. 着手可能性を分類する

| 判定 | 基準 |
|---|---|
| `着手可能` | 望まれる成果が具体的、範囲が限定、文脈が十分、open、ブロックされていない、検証できそう。 |
| `要確認` | 目的はもっともらしいが、プロダクト上の意図・再現手順・受け入れ基準が欠けている。 |
| `ブロック中` | blocked とマークされている、担当が所有権を意味する形で他者に割り当てられている、外部アクセスに依存している、メンテナの判断が必要。 |
| `並列不可` | 本当の順序依存にのみ使う: 選ばれた別の issue の成果が出るまで着手できない場合。同じファイルに触れることは **理由にならない** — 重なる作業は並列で割り当て、マージ時に調整する。 |

候補は、issue 番号・URL・タイトル・根拠・触れそうな領域・検証の手がかり・リスクとともに報告する。
依頼で自動選択が明示的に許可されていない限り、どの issue を割り当てるかユーザーに尋ねる。

### 5. Commander 経由で割り当てる

issue を選び終えたら、指揮官の振る舞いに切り替える:

- 選ばれた issue を独立した単位に分解する。
- プロンプトを書く前に隔離モードを決める (下記)。
- 独立した単位は 1 つのメッセージで並列に割り当てる。
- 各プロンプトに issue の文脈・関連コメント・範囲・制約・報告形式を入れる。
- 完了を主張する前に、サブエージェントの報告を読み取り専用で検証する。

#### まず隔離モードを選ぶ

| 単位数 | モード | 理由 |
|---|---|---|
| 1〜2、ファイルが明確に分かれている | 共有ツリー + ファイル分割 | マージ工程が不要、単位ごとの依存インストールも不要。 |
| **3 以上、またはファイルの重複あり** | **worktree 隔離** (`isolation: "worktree"`) | エージェントが制約なく作業でき、コンフリクトは最後に一度だけ解消する。 |

単位が 3 つ以上になった時点で worktree 隔離を既定にする。ファイル分割は安く見えるが、
すべてのエージェントに税を課す:

- リポジトリ全体の `fmt` / `lint --fix` / `check` / `build` を禁止しなければならない。
  他のエージェントが編集中のファイルを書き換えてしまうため。
- ファイルを共有する単位は、今すぐ走らせる代わりに後の波へ回される。
- 自分のレーン外のファイルが必要になったエージェントは止まり、報告して戻ってくるしかない。

worktree 隔離のコストは worktree ごとの依存インストールと最後のマージ。たいていはそちらが良い取引で、
ユーザーもそれを期待していることが多い。どちらのモードを選んだかは、推測させずに明言する。

#### コミット方針はモードによって変わる

- **共有ツリー:** コミットを禁止する。変更は 1 つのツリーに集まり、ユーザーが合成 diff をレビューする。
- **worktree 隔離:** エージェント自身の worktree ブランチへのローカルコミットは **必須**
  — worktree 内の未コミット作業は統合できない。`push` と PR 作成は禁止し、`main` / 作業ブランチ /
  救出ブランチへの切り替えと変更も禁止する。

いずれの場合も、ユーザーがその状態変更を依頼しない限り、`gh issue` のラベル・担当・クローズは禁止のまま。

`gh issue comment` には常設の例外が 1 つある。**単位が PR に到達しないまま終わる場合
— ブロックされた、根本原因が見つからない、テストが緑にならない、プロダクトの判断が必要 —
エージェントは黙って終えてはならない。** `gh issue comment <n>` で、issue が書かれている言語で、次を含む知見を issue に投稿する:

- 分かったこと、
- 試したこと、
- 両者の根拠 (数値、失敗出力、スクリーンショット)、
- なぜ PR に到達しなかったか、
- 次に推奨する選択肢。

作業が PR に到達した場合はコメント不要 — PR 本文の `Closes #N` が役割を果たす。会話ログは報告ではない:
issue に着地しなかった調査は、エージェントが終了した瞬間に失われる。

#### すべてのプロンプトに入れる価値のある他の制約

- **開発サーバーのポートはマシン全体で共有される。** 各エージェントに固有のポート (5181, 5182, …) を
  割り当て、サーバーを終了させるよう伝える。さもないと 2 番目に起動したエージェントは黙って別の場所に
  バインドするか失敗する。
- **ベースラインの数値。** 手順 2b で得た変更前のテスト件数と型チェックの状態を渡し、
  自分のリグレッションと既存の問題を区別できるようにする。
- **補正後の行番号** (issue 本文からずれている場合)。
- **重複は想定内であり禁止事項ではない。** 他のエージェントが今まさに同じファイルを編集しているかもしれない
  ことを各エージェントに伝える。それは停止・許可待ち・修正範囲の縮小の理由には決してならない —
  コンフリクトはブランチのマージ時に解消する。
- **最小の diff**。まさにその重複があるからこそ: ついでの再フォーマットも、無関係な整理もせず、
  issue を閉じる最小の変更にとどめる。マージを読めなくするのは重複そのものではなく、変更の膨張。
- **不達時の報告。** 単位が PR に到達しない場合、エージェントは肩をすくめて終わるのではなく、
  知見を issue の言語でコメントする。

割り当てプロンプトはこの形を使う:

```text
目的: <issue #N にとって完了とはどういう状態か>
issue の文脈: <番号、URL、タイトル、ラベル、本文の要約、関連コメント>
ベースライン: <ブランチ、HEAD の sha、テスト件数、型チェックの状態、補正後の行参照>
環境: <worktree 隔離か共有ツリーか、インストール手順、許可されたコマンド、
割り当てられた開発サーバーのポート>
範囲: <許可するファイル/領域、許可しないファイル/領域、状態変更の制限>
共有ファイル: <いま動いている他の単位と、それらが触りうるファイル。重複は想定内
— diff は最小に保ち、それで止まらないこと>
制約: <このモードでのコミット方針。push・PR・ラベル・担当・クローズは禁止。
PR に到達する成果が出ない場合は、`gh issue comment` で issue #N に、issue の言語で知見をコメントする>
報告形式: 変更ファイル、実行したコマンドと結果、リスク、ブロッカー、
未解決の疑問、検証の証拠。
```

## クイックリファレンス

| やりたいこと | 操作 |
|---|---|
| issue を探す | リポジトリ固有のラベル/検索で `gh issue list`。 |
| 文脈を確認する | `gh issue view <n> --comments --json ...`。 |
| ベースラインを確認する | `git status -sb`、`git log --oneline -1 origin/main`、挙げられた行を実際に解決する。 |
| 着手可能性を判断する | 具体的な成果、限定された範囲、文脈、検証手段、ブロッカーで判断する。 |
| 作業を割り当てる | `commander` を使う。実作業は委譲し、検証は読み取り専用に留める。 |
| ファイルの重複を扱う | worktree 隔離のうえで構わず割り当て、コンフリクトはマージ時に解消する。 |
| 行き詰まりを締める | `gh issue comment <n>` に issue の言語で: 分かったこと、試したこと、根拠、なぜ PR に至らなかったか、次の選択肢。 |

## 危険信号

- 明示的な許可なく issue を自動選択した。
- メンテナの判断や重複の指摘を含みうる issue のコメントを無視した。
- 挙げられたファイルと行が *このチェックアウト* に存在するか確認していない。
- HEAD が detached、または `origin/main` から分岐しているのに、そのまま割り当てた。
- 3 つ以上の単位を 1 つの共有ツリーに入れようとしている。
- 2 つのエージェントが同じファイルを編集するかもしれないという理由で、単位を逐次化・破棄したり、
  ユーザーに選ばせたりした。
- エージェントが PR も issue へのコメントも残さずに終わった。
- 指揮官モードだと言いながら、自分で実装作業をしている。
- サブエージェントのプロンプトに issue の文脈・範囲・制約・報告形式が欠けている。

## よくある失敗

- **ラベルを真実として扱う:** コメントがラベルを上書きしていることがある。有望な issue は
  `gh issue view --comments` で確認する。
- **チェックアウトを信用する:** issue が前提としたツリーと、いま自分がいるツリーは別々の主張。
  issue に書かれた機能が未マージのブランチにあることもあり、その場合その「着手可能」な issue には
  編集する対象が存在しない。選択の前、手順 2b で検証する — 誤ったツリーの上で作った候補リストは、
  ユーザーには見えない形で間違っている。
- **ファイルの重複をブロッカー扱いする:** 2 つの issue が 1 つのファイルに触れるのは、実行すべき
  マージであって、単位を逐次化・破棄したり、ユーザーに選ばせたりする理由ではない。両方を割り当て、
  worktree で隔離し、最後に調整する。
- **行き詰まりを会話ログの中で死なせる:** PR を生まなかった単位も知識は生んでいる。
  それが issue に無ければ、次のエージェントはゼロから始めることになる。
- **反射的にファイル分割へ手を伸ばす:** 2 単位までは正しい判断だが、それを超えるとすべての単位への
  税になる。モードは意図して選び、どちらを選んだかユーザーに伝える。
- **worktree 隔離でコミットを禁止する:** 作業が戻ってくる手段を失う。エージェント自身のブランチへの
  ローカルコミットを必須にし、代わりに push と PR を禁止する。
- **割り当てが早すぎる:** 自動選択が明示的に許可されていない限り、候補を提示して選んでもらう。
- **プロンプトの記述不足:** サブエージェントはコールドスタートする。issue の文脈、制約、
  他に選ばれた issue、正確な報告項目を含める。
